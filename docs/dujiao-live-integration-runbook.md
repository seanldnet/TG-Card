# Dujiao-Next 真实商户联调操作手册（PR E）

> 本文是待执行的真实环境操作规程，不是测试已完成的声明。真实扣款、采购、回调和失败退款必须由项目所有者在受控环境执行。mock 测试、CI 通过或镜像发布均不能替代真实商户验收。

## 0. 阶段边界与前置条件

PR C 采购队列/幂等/查单回调/失败退款、PR D 供应商资金核对/退款账本/uncertain 治理、PR U 分页同步/来源总闸、PR S 安全与运维补欠均已合并。PR S main Docker Publish #44603594008 已成功，GHCR 多架构 latest digest 为 sha256:f9f1dd001bd90c743264d3d16655226626842805f6f8af108c27eb8ff1b639ac；部署和真实验收仍需项目所有者执行。

禁止在聊天、工单或验收表中记录 API Key、API Secret、Bot Token、JWT Secret、数据库 DSN、买家完整支付凭证或交付明文。

建议使用独立测试买家、独立 Telegram 对话和供应商明确标记的测试 SKU。每笔测试订单数量为 1，金额采用供应商允许的最低可行金额。

开始前逐项确认：
1. 已部署包含 PR C/D/U/S 的镜像，记录镜像 tag、digest 和 main commit。
2. 在 Compose 项目目录执行 bash scripts/backup.sh；确认备份目录含 postgres.dump、tg_card_data.tar.gz、SHA256SUMS、manifest.txt。
3. 服务器已启用 NTP。Dujiao 回调时间戳容差为 ±60 秒。
4. 管理员能访问“上游 / Dujiao-Next”配置页和采购队列。
5. TG-Card 有有效 HTTPS 公网域名，证书链有效，DNS 正确，443/TCP 对 Dujiao 回调来源可达。
6. 如经反向代理，TRUSTED_PROXY_CIDRS 只填写实际代理来源 CIDR。
7. 管理员认证后调用 GET /api/health/detailed，确认 database.connected=true、paymentWatcher.enabled=true，并查看 lastScanAt。
8. 测试买家已向目标 Bot 发送 /start，Bot 可向买家发送交付/退款通知。

任一前置条件不满足，先排除问题，不要用真实订单排查基础网络。

## 1. Dujiao-Next 凭证与站点配置

在 TG-Card 管理后台的“上游 / Dujiao-Next”页面配置：
- Base URL：填写供应商站点 HTTPS 根地址，例如 https://supplier.example。不能附加 /api/v1/upstream、其他路径、查询参数或片段。
- API Key / 商户 ID 与 API Secret：由 Dujiao-Next 商户后台或供应商管理员签发，直接录入后台，不通过 SQL 修改。
- Callback URL：填写 TG-Card 公网 HTTPS 地址，路径必须精确为 /api/v1/upstream/callback，例如 https://shop.example.com/api/v1/upstream/callback。不得使用 HTTP、localhost、私网 IP、额外路径、查询参数或片段。
- 查单间隔默认 30 秒（范围 5–3600 秒）；采购超时默认 30 分钟（范围 1–1440 分钟）。
- 供应商低余额阈值使用供应商账户原币单位，0 表示关闭阈值告警。
- 若上游币种为 USDT，汇率填 1；其他币种必须人工核实“1 单位上游币种 = ? USDT”，不得猜测或自动抓取。
- 核对百分比加价、固定加价、汇率和买家最终售价。

保存后点击“测试连接”。必须核对站点名称、账户标识（接口有返回时）、余额和币种。连接测试失败不得启用上游售卖。

## 2. HTTPS 回调与公网可达性

### 2.1 反向代理要求

精确转发 POST /api/v1/upstream/callback 到 TG-Card。代理必须：
- 使用有效 HTTPS 证书，不要依赖 HTTP 跳转。
- 原样保留请求 body 字节，不要解析后重新序列化 JSON。
- 原样转发 Dujiao-Next-Api-Key、Dujiao-Next-Timestamp、Dujiao-Next-Signature 三个请求头。
- 不添加 Basic Auth、验证码、浏览器挑战或后台登录要求；应用自身负责 HMAC 验签。
- 不改写路径、不添加尾部斜杠、不转发到 SPA。
- 允许 POST，请求体不得超过应用 1 MiB 限制。
- 不要把 API Secret、完整签名或交付 payload 写入访问日志。

### 2.2 从外部网络检查 TLS 和路由

在 TG-Card 服务器以外执行：

    curl -i --max-time 15 https://shop.example.com/api/v1/upstream/callback

该路由只注册 POST，因此 GET 返回 405 Method Not Allowed 是应用路由已到达的预期结果。证书错误、DNS 失败、超时、代理 404、跳转登录页或返回前端 HTML 均未通过。此探测不会提交伪造回调，不触发验签失败告警，也不会修改订单。

GET 405 只证明 TLS/路由可达，不证明供应商真实 POST 可达。最终必须由 Dujiao-Next 对真实测试订单投递 POST 回调，且 TG-Card 采购事件中出现已接受的回调事件，才算端到端通过。

### 2.3 验签规则与排查

应用使用：
- Dujiao-Next-Api-Key 与后台 API Key 恒定时间比较。
- Dujiao-Next-Timestamp 为 Unix 秒，时间差必须在 ±60 秒内。
- 对原始 body 计算 MD5 十六进制值。
- HMAC-SHA256 签名原文为以下四行，以换行符分隔：

    POST
    /api/v1/upstream/callback
    {timestamp}
    {body_md5}

- API Secret 是 HMAC 密钥，签名恒定时间比较。
- 回调业务事件另有稳定 SHA-256 幂等键，重复事件不会重复交付。

验签失败先核对服务器时间、路径、Key/Secret 配对和代理是否修改 body/headers。不得关闭验签或放宽时间窗口来绕过问题。

## 3. 同步目录并启用上游售卖

1. 在上游页面启动一次手动同步，观察批次进度、已处理数和错误数。
2. 等待同步完整成功；数千商品时不要连续点击重复启动。
3. 核对分类、商品、SKU 数量、图片、库存、原币价格、币种、汇率和加价。
4. 选择一个供应商确认可自动交付的 auto SKU。不要使用 manual SKU；manual 动态表单尚不支持买家自助采购。
5. 在 Bot 中确认只展示上游目录，分类/商品分页正常，详情价格与后台一致。
6. 同步成功后再打开“启用上游售卖”。启用后 Bot 只售卖上游商品；本地商品保留但不参与当前售卖。
7. 修改站点、凭证或价格策略前，必须先执行“停用并清除上游数据”，回到本地来源后再重新配置、同步和启用。不要绕过总闸改数据库。

## 4. 正常路径：最低金额真实采购

### 4.1 下单前记录

记录供应商余额基线（金额、币种、UTC 时间）；确认余额足够且没有其他同时发生的扣款/充值；记录 TG-Card 售价、上游 SKU 原价、汇率、加价和数量 1；确认买家 Bot 已启动且支付方式可用。

### 4.2 执行步骤

1. 测试买家在 Telegram Bot 选择 auto SKU，数量 1，创建本地订单。
2. 买家按正常流程完成真实支付（TRC20 USDT 或已确认可用的站内余额支付）；不要直接改订单状态或数据库。
3. 等待支付监听器确认付款。订单应进入 procurement_pending，采购队列出现同一笔本地订单。
4. 等待采购 worker 调用 Dujiao-Next。核对 downstream_order_no 与 TG-Card 本地订单号一致，记录上游订单 ID/订单号。
5. 等待供应商真实回调或查单轮询推进到 delivered/completed；交付内容应加密保存后经 Telegram 发给买家。
6. 测试买家确认收到交付；核对本地订单状态、交付时间、采购事件和回调事件。

### 4.3 正常路径验收

- 只创建一笔本地订单和一条有效采购映射；重复支付通知/回调不得重复采购或交付。
- 原支付记录、金额和交易引用保持不变。
- 供应商余额变化与 SKU 采购金额相符；如有其他资金活动，不得把全部差额归因于本订单。
- PR D 采购前/后余额快照和资金检查可按本地订单号关联；差异、缺快照或币种不一致应进入异常中心并通知 Owner。
- 资金检查只告警，不自动调整买家或供应商余额。

## 5. 失败路径：人工队列、退款账本与审计

**必须先与 Dujiao-Next 供应商协调专用失败测试 SKU。** 优先使用“目录仍显示可售、下单时稳定返回业务拒绝”的测试 SKU，并由供应商确认失败不会扣供应商余额。若只能通过零库存触发拒绝，则先在 TG-Card 同步到可售快照，再由供应商在上游将该测试 SKU 设为零库存/禁售，确保本地目录尚未重新同步且测试在下一次自动同步前完成。不要用主力商品、错误 API Secret、断网、强杀容器或修改数据库制造失败；网络超时可能造成供应商已受理但本地未取得响应的 uncertain 状态。

1. 确认测试买家、失败 SKU、数量 1 和最低金额；再次记录供应商余额基线。
2. 测试买家创建订单并完成真实支付。
3. 等待供应商返回明确业务拒绝/不可购买结果。TG-Card 应将订单置为 procurement_failed，采购记录进入人工队列并记录失败原因。
4. 核对原支付记录仍存在，支付金额和交易引用未改变；采购失败本身不得自动扣减、吞掉或退款买家资金。
5. 在管理员“上游采购队列”找到订单，核对本地订单号、供应商返回信息和采购事件。在确认退款前不要再次点击重试。
6. 管理员执行一次“退款”，填写明确原因，例如“PR E 失败测试 SKU 不可购买”。系统将金额退回买家站内钱包（不是自动链上原路退回），写独立退款账本、采购事件和管理员审计，并通知买家。
7. 核对订单为 refunded，只有一条 upstream_procurement_refunds 记录和一笔对应 wallet credit。再次退款应被拒绝，不得产生第二笔 credit。
8. 检查 admin_audit_logs 中的管理员、原因、时间和退款动作；检查采购事件中的失败与退款闭环。

### 5.1 uncertain 例外

网络超时/响应丢失可能进入 uncertain，不能当作供应商未受理。先在 Dujiao-Next 商户后台按本地 downstream_order_no 核实：
- 已受理：在 TG-Card uncertain 人工核实入口填写真实上游订单 ID，恢复查单；不得重新创建订单。
- 确认未受理：记录人工核实说明，再按原本地订单号幂等重试，或按规则退款。
- 无法确认：暂停订单，不重试、不退款、不改余额，通知 Owner 和供应商继续核实。

## 6. 停止条件与资金红线

出现以下任一情况，立即停止新测试订单并保留证据：
- 同一订单出现多个上游订单 ID、重复供应商扣款或重复买家交付。
- 供应商余额差异无法解释、币种不一致或采购后余额快照缺失。
- 订单支付金额、原支付引用、钱包余额或退款流水出现非预期变化。
- 回调验签失败、回调重复处理导致状态倒退，或 delivered 回调缺少交付 payload。
- uncertain 订单无法确认供应商是否受理。

停止后不得手动 SQL 修改订单/钱包/供应商余额/退款记录，不得盲目重试或重复退款，不得自动冲账/补款。先处理在途采购，再决定是否通过来源总闸停止新售卖。未盘点在途订单前不要触发上游目录清理。

## 8. 阶段验收判定

只有以下项目均有真实证据且项目所有者确认后，才可记录“真实商户联调通过”：

- [ ] HTTPS 回调 URL 从公网可达，Dujiao-Next 真实 POST 回调通过验签并正确处理。
- [ ] 真实最低金额 auto SKU 采购成功，供应商扣款、订单映射、交付和买家收货一致。
- [ ] 重复支付通知/回调不会重复采购或交付。
- [ ] 供应商余额前后快照与采购金额可核对；未解释差异进入异常中心且没有自动冲账。
- [ ] 供应商明确失败测试 SKU 能进入采购人工队列；买家原支付记录保持不变。
- [ ] 人工退款只生成一笔退款账本和一笔钱包 credit；重复退款被拒绝。
- [ ] 失败/重试/退款均有采购事件与管理员审计记录。
