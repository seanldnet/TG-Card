# TG-Card 产品路线图：智能化运营与基础设施演进

> 规划基线：2026-11-23（按 PR #140/#142 合并状态校准）。项目形态保持单站点、单运营者；不引入多用户、多租户或复杂 RBAC。路线图描述目标与验收边界，不代表功能已经实现。

## 总体原则

- 分阶段、独立 PR、独立测试；每批合并后更新 `PROJECT_STATUS.md` 与 `CHANGELOG.md`，并按项目流程构建发布镜像。
- 优先复用现有售后工单、Owner Bot、订单/履约状态机与密钥管理能力，不另建平行业务流程。
- 密钥、订单凭据和用户隐私按最小权限原则处理；外部 API 调用必须有超时、限额、审计和失败兜底。
- 兼容当前单机部署；Redis、对象存储均为可选依赖，未配置时保留当前本地实现。
- 任何未取得官方 API 证据的上游平台，不猜测协议、不伪造适配能力。

## P1：智能化与省心运营

### P1-1 / P1-2：LLM AI 售后客服与多模型适配

目标：在现有 Bot 售后入口提供 AI 前置答疑，未解决时转入现有 Owner Bot 工单。

范围：
- 建立统一 LLM Provider 接口，适配 OpenAI、DeepSeek、Kimi、智谱等常见服务；按各家官方兼容协议实现请求格式、鉴权、模型名、错误映射和超时处理，不能假设所有供应商完全兼容。
- 后台配置供应商、API Base URL、模型名称、API Key、启用状态及连接测试；API Key 加密存储，读取接口仅返回配置状态。
- 支持后台配置 AI 角色 Prompt；将关联订单必要字段、商品说明和售后规则作为受控上下文，不向模型发送不必要的密钥、支付凭据或其他敏感数据。
- AI 仅提供解释与操作指引，不得直接退款、改订单、补发卡密、修改余额或执行任何资金/履约操作。
- 用户要求人工、提及退款/支付争议、命中敏感规则、模型超时/不可用、置信度不足或无法解决时，停止自动答复并交接现有 Owner Bot 工单流程。
- 工单/后台记录 AI 前置处理状态与转人工原因（本批已实现独立状态表、列表标记及筛选）；模型/供应商调用审计、摘要和成本控制仍需后续完善，避免无限对话和重复创建工单。
- 设置最大轮数、输入/输出 token 上限、速率限制、调用超时、成本控制和失败降级；AI 不可用不得阻断用户提交售后。

验收：
- 覆盖常见使用问题、未收到卡密、订单状态解释；订单上下文必须与当前用户及订单严格绑定。
- 退款/人工/敏感意图必转人工；模型异常时仍可创建现有工单。
- API Key 不回显、不写日志；Prompt 注入不能越权调用业务操作。
- 至少对每家已配置供应商完成 mock/契约测试；真实联调需使用运营者自行申请的 API Key。

### P1-3：Telegram Bot 中英文 i18n

- 抽取 Bot 用户端硬编码文案，建立中文/英文语言包和统一翻译函数。
- Bot 设置增加默认语言；`/start` 时优先按 Telegram `language_code` 匹配支持语言，不支持时回退默认语言。
- 用户可主动切换语言；语言偏好持久化，后续交互一致。
- 商品、订单、错误提示、售后通知等动态文案统一使用语言层；缺失翻译有明确 fallback。
- 验收：新旧用户、未知语言、缺失翻译、重启后语言保持及主要用户流程中英文回归。

### P1-4：管理后台 Vue i18n

- 引入 `vue-i18n`，建立 zh-CN/en-US 语言包；提供右上角语言切换。
- 覆盖菜单、页面标题、表单、按钮、校验、通知、空状态和关键业务状态，不只翻译首页。
- 语言偏好本地持久化；默认中文；动态服务端错误提供稳定错误码到本地文案映射。
- 验收：主要后台页面无明显硬编码中文/英文混杂，切换语言无需重新登录，移动端布局不回退。

### P1-5：上游发卡 Provider Adapter

- 定义通用 Provider 能力边界：连接测试、余额、目录/商品/SKU、同步、采购下单、查单、取消（若上游支持）、交付结果及回调。
- 将现有 Dujiao-Next 实现封装为首个 Provider，保证当前目录同步、auto/manual 采购、幂等、失败处理和交付行为不退化。
- 后台可配置 Provider 类型与各自凭据/地址，凭据加密保存；支持启停、连接测试和明确能力标识。
- ACG-Faka（异次元）作为候选 Provider：只有取得并核实官方商户 API 文档、认证、目录、采购、查单/回调和交付语义后，才实现真实适配；未确认前只保留接口扩展点，不虚构 API。
- 验收：Dujiao 现有真实流程回归；Provider 切换不会串用商品、订单或密钥；不支持的能力明确禁用。

## P2：高并发与运维架构演进

### P2-1：Redis 可选依赖与分布式协调

- 新增可选 Redis 配置、连接健康检查、TLS/认证支持和运维说明。
- Redis 配置启用时，将 IP 限流、Bot 轮询租约、订单交付租约切换为共享实现；未配置时继续使用现有单机实现。
- 使用原子操作/租约 token、TTL、续租与 fencing/idempotency 设计，防止锁过期后旧持有者继续执行造成重复交付。
- 明确 Redis 不可用时各机制的 fail-open/fail-closed 策略；资金与订单交付关键路径不能因降级产生重复执行。
- 验收：多实例并发测试、进程崩溃/锁过期/Redis 断线测试、限流共享测试及重复交付防护；仍是单运营者业务模型。

### P2-2：S3 兼容对象存储

- 支持 S3 API 兼容服务，包括 AWS S3、Cloudflare R2 及兼容 OSS 网关；配置 endpoint、region、bucket、凭据、路径前缀和访问策略。
- 新上传商品图片与附件可直接写入对象存储；上游图片同步可选择本地或对象存储。
- 抽象统一 Storage 接口，保留当前本地存储后端；通过配置选择后端。
- 规划已有文件迁移、对象校验、失败重试、删除/孤儿清理、私有对象访问和 URL 生命周期；不得因切换存储导致历史商品图/附件失效。
- 验收：上传/读取/删除、权限与签名 URL、失败恢复、旧文件兼容和本地↔对象存储迁移演练。
